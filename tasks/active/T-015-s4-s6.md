Passing entries require meaningful output evidence; failure for an omission may use null. A schema-valid but incomplete/contradictory witness set fails validation. [E2, E8]

### Bounded state machine and fallbacks

- Initial writer: one logical call. Validate structure before attempting verifier. One verifier logical call per structurally eligible draft if gated; no stage-level verifier re-ask after malformed/failed output. Mark unavailable verification, then bounded fallback; do not misclassify verifier transport failure as a repairable content finding.
- For content/structural failures with a usable draft, iterate `range(validation.max_repairs)`: send failed entries plus that draft as data to the writer under the same admin system bytes; count the round when its writer attempt starts; rerun **all** structural and semantic obligations on the new draft. Stop on pass, exhaustion or an unrecoverable call failure. No recursive repair calls and no independent schema retry counter.
- A writer schema-invalid result currently loses its raw text at the client boundary. Repair may resend the original brief and recorded structural failure, without inventing a draft; it still consumes one repair round. Refusal/truncation/deadline/HTTP failures go directly to fallback rather than resubmitting an unavailable draft. If raw malformed text is retained later, it must stay diagnostic data and be explicitly covered by the contract. [E5]
- Try each recognized `validation.fallbacks` entry in configured order. Minimal template (Q3) is deterministic, validated, always degraded. Original user prompt stays verbatim and is returned degraded only if its type and the profile's mandatory structural contract permit it; a JSON-only profile cannot receive an arbitrary string masquerading as valid JSON. A fallback can explicitly leave semantic obligations unverified in the trace; it cannot claim success. `failed` terminates with null output; exhaustion also fails. Unsupported/duplicate fallback names refuse configuration.

### Calls, retries and budget accounting

Let `R = validation.max_repairs`, `G` be the inline-verifier decision, and `M` be a post-response monitoring selection (only when `G` is false).

| Scope | Logical generation bound | Failure path |
| --- | --- | --- |
| S4 initial draft | 1 writer | Complete/OK -> structure; invalid -> bounded repair if possible; other failure -> fallback. |
| S5 including repairs | At most `R` additional writers and `G * (1 + R)` verifiers | Every failed attempt is recorded. No verifier call after a structurally rejected draft. No hidden retry of an invalid verifier reply. |
| Deferred monitor | At most `M` verifier; no writers or repair | Monitoring failure is diagnostic only and never revises the delivered status. |
| S4-S6 total | `1 + R + G*(1+R) + M`, at most `2*(1+R)` because `M=0` when inline | Minimal/user fallbacks spend zero model calls; S6 spends zero. Clarification spends zero S4-S6 calls. |
| S2 (outside this bound) | Up to `2*(1 + planner.second_chance_rounds)` | Existing one invalid-reply retry per planner round; no retry for failed model calls. Dense query embeddings are separate. [E7] |

Each logical generation can reach selected backend then configured default through existing budget/image policy. HTTP attempts per visit are bounded by `1 + backend.http.max_retries`; probes are bounded by backend `probe.max_requests` and probe timeouts, shared across roles in the run. A conservative wire bound is the sum of those attempt limits for each reachable backend visit plus its total probe allowance; report observed probe/generation/retry counts separately. Never advertise the logical-call bound as a total network request count. Every cloud attempt/probe consumes the shared ledger, including retries; exhausted budgets either stop or use the configured local fallback with `BUDGET_EXHAUSTED`. [E5]

RES-1 changes transport retry semantics to connect-only. Re-read the integrated transport before P1: the current base retries `httpx.TransportError` and configured HTTP statuses. T-015 must not reimplement either policy or layer an extra retry around it. No total request deadline is currently enforced by S4-S6; propose explicit `runtime.request_deadline_s` for the coordinator and bounded drain for post-response work, rather than treating S0's stage-boundary intake deadline as an HTTP cancellation guarantee. [E5, E11]

## S6 status and diagnostics

Apply this table in order; choose exactly one status. Degradation causes remain independent from the checked draft's local result, so later repairs cannot erase an earlier stage failure. [E3, E7, E11]

| Input condition | Status / output |
| --- | --- |
| S0 refusal or no usable output after permitted fallbacks; unrecoverable deadline/refusal/truncation | `failed`, output null. Preserve source binding only if successfully prepared. |
| Valid plan asks for clarification and `clarification.mode=ask` | `needs_clarification`, output null, no writer/inline verifier; candidates in trace. Fatal S0 refusal above takes precedence. |
| `best_effort` ambiguity with usable output | `degraded`; never needs_clarification. |
| Usable output plus S0/S1/S2/S3 failure/degradation, unavailable mandatory verification, budget fallback affecting the chosen path, or explicit S5 fallback | `degraded`, even if its local draft passes after repair. |
| No prior degradation; at least one repair round; complete checked output passes every required check | `repaired`. |
| No prior degradation; first complete draft passes every required structural and gated semantic check | `success`. |

`PARAM_UNSUPPORTED` is a trace warning, not automatically a degraded status when an unsupported optional field is legitimately dropped; mandatory capabilities/schema/independence checks still fail closed. Trace the actual effective settings. [E1, E5]

[E6, E7, E11]

Keep existing envelope top-level `warnings` for its six allowed protocol codes; store all richer stage codes, error details, clarification candidates, per-entry verdicts, repair/fallback history and monitoring results in the trace row's JSON `body` and `warnings`. [E3, E8, E10]

Build the envelope/row on the response path; enqueue durable trace writing without awaiting disk I/O there. Use a caller-owned bounded lifecycle: explicit start, submit, after-delivery monitoring, drain/close; no fire-and-forget coroutine that disappears at `asyncio.run` exit. Attachments require a successful snapshot hold before the original lease is released; failed hold means no dangling attachment and an explicit degraded/failed response. Retention cleanup releases holds and removes expired trace segments through anchored storage operations. Off-path trace persistence touches only `storage.data_root`, never KB paths. [E3, E10]
