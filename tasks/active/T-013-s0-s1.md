### Proposed schemas and library boundary

- **`request.v0.schema.json`:** closed object; required `prompt` string and `task` enum generate/edit, optional `profile_id`, optional single `source_image`, optional `overrides` dotted-key mapping. Preserve every accepted prompt string exactly, including empty/whitespace strings and multilingual structured-looking text; do not strip, normalize, parse or extract options from it. Proposed JSON representation of the image is base64 bytes (or null/absent); strict decode is implemented explicitly, not assumed from JSON Schema's `contentEncoding` annotation. No URLs or input paths, and no dimensions/ratio fields. The library decodes data it is given and does not open a request-specified image file.
- **`intake_result.v0.schema.json`:** closed serializable payload with request ID, untouched prompt, task, resolved profile ID, effective configuration and its hash, optional prepared source-image payload plus image ID/role, snapshot ID, intake retrieval state, warnings, outcome, and error/refusal envelope on refusal. Distinguish intake-ready from a final successful enhancement; use an intake-only `pinned` state until S1/S3 establish retrieval results. Missing snapshot carries degradation and warning. All nested required fields and variant consistency are validated; reuse the existing response schema for refusal, not a competing failed-envelope schema.
- **`IntakeResult` library owner (proposal):** serializable payload plus checked `ProfileView` and optional live `PinnedSnapshot`; context manager/explicit close keeps the pin available to later stages and releases on caller exit. Do not put live handles into JSON or release a successful pin before returning it. Refusals retain no lease. No gateway/store/index is constructed on the off branch; on branch the minimal knowledge boundary owns the single pin for later P2 access, without implementing candidate search.
- **Identity (agrees with PM):** request ID generated independently of prompt text; source image ID is a digest of original input bytes, preserved across client preparation. Record prepared payload separately. Structural IDs/constants are protocol/artifact-bound; no textual keyword contributes configuration or task choice.
- **Configuration schema:** extend required fields for independent pixel bound, intake deadline and the approved permission policy; update full/dev examples and ownership documentation together. Keep existing response-envelope schema unchanged under question 2's proposal.

### Proposed shortlist schema and library boundary

`candidate_shortlist.v0` is a closed JSON object with required `snapshot_id` (pinned ID or null), `state` (`ready` or `failed`), `candidates` array and `error` (null or closed `{code, message}`). A successful empty list is `ready`, not a backend failure. This S1-local status does not claim final `retrieved` or `no_match` before the planner. Missing S0 snapshot and operational index/embedding failures return `failed`, empty candidates and a structural error; no partial shortlist is labelled successful. The future coordinator owns final response retrieval state. Q5 asks approval of this boundary.

Each entry has exactly `concept_id`, `name`, `kind` (existing kind enum or null), `description` (one-line string or null when no source description exists), `matched_source` (`name`, `alias`, `lexical`, `dense`) and `matched_span` (closed `{start, end, text}`). Offsets are half-open Python code-point positions in the original prompt, and `text == prompt[start:end]`. Validate cross-field offsets, unique concept IDs and snapshot identity in addition to JSON Schema. Empty prompt produces a valid empty list without an empty encoder call.

Metadata comes from the same pin: canonical `concepts.display_name/kind` (`storage/tables.py:79-85`), first non-null membership description in stable `(folder_id, concept_id)` order, collapsed to one line by whitespace structure only; otherwise null. No generated summary, fallback meaning, arbitrary character cutoff or description model call. Q4 asks approval because the stage prose does not specify multiple/null descriptions.

Proposed async entry: `build_candidates(intake_result, *, embedder=None)`. Effective configuration and project root come from S0/pinned ownership; no independently supplied prompt/config can drift. Check the effective retrieval gate first. Calling with retrieval off raises a programming-error `ValueError` before index/store/encoder construction; a refused/closed/inconsistent S0 result also refuses. An enabled but missing snapshot follows S0 degradation. An enabled dense source requires an explicit compatible encoder in this phase; no default creates a server or silently falls back. Supplied encoder and S0 lease stay caller-owned, including on failure/cancellation. Programming/configuration/space errors raise precise structural exceptions before queries; operational retrieval failures become the schema-valid failed result.

### Window construction, fusion and bound (proposed)

1. Preserve prompt bytes/text at the S0 boundary. Enumerate original nonempty code-point spans once for each width `1..L`, start `0..L-width`. For each slice call K5 exact equality after its shared normalization. This covers names without separators and length-changing NFKC/casefold without language tokenization. Build canonical-name/accepted-alias metadata maps once from the pin; never test every name against every window.
2. Whole prompt is one lexical/dense query. When `segment_prompt` is true, add deduplicated nonempty comma/line spans and JSON scalar value spans, traversing JSON structure rather than treating keys/values as configuration. For valid JSON, a structural token scanner plus the stdlib decoder retains raw token offsets and decoded string values (including escapes, duplicates and nested values); keys are not extra semantic queries. For non-JSON text use comma/line structure. Never use a natural-language regex. A decoded JSON query's reported span covers its original token, so its evidence remains an exact raw substring. Verify installed stdlib decoder behavior before relying on its token APIs during implementation.
3. Budget before expensive lookup/embedding: raw exact spans total `L*(L+1)/2`; add structural decoded exact lookups and the whole/segment query units. Require total <= configured `max_prompt_windows` before retrieval calls; count only work for enabled sources and deduplicate structural units by `(start,end,query_text)`. Generate raw windows lazily. Over-budget refusal is explicit, never silent truncation. If all sources are off or shortlist size is zero, validate configuration then return empty without index/encoder work. Q1 asks approval of this additional key and refusal.
4. Bound is independent of number of names: after a single O(catalogue rows + text) metadata pass, at most W exact probes and Q lexical queries, with `W+Q <= max_prompt_windows`. K5 exact currently also validates n-grams, so CPU character work is O(sum of window lengths), not falsely O(W); exhaustive windows can be cubic in L but are admitted only under the explicit work budget. Dense makes at most `2*Q` bounded K5 searches across text/image tables, each with the configured dense depth, and sequential batches no larger than `embedding.batch_size`. K5 visits blocks, not all-pairs matrices. Assert operation counts while growing synthetic catalogue size; no timing/production scalability claim.
5. Produce one unique-concept ranked list per enabled source. Alias/name exact matches are tied then ordered by concept ID; lexical uses the best matched-gram count, dense the best score across whole/segment queries and text/image embedding tables, with ID ties. Per-query K5 dense k and final source-list caps both use that source's depth. Repeated rows, windows or modalities never add another vote. This bounded row-depth policy can return fewer unique concepts when many rows share one concept; document it rather than invent an overfetch factor.
6. Proposed RRF contract: `score(c) = sum(1 / (rrf_constant + rank_s(c)))` for each enabled source containing c, ranks starting at 1. Accumulate in deterministic source order, tie by concept ID, then cap at `shortlist_size`. Preserve deterministic representative evidence by best source rank, source label, start/end; choose `name` before `alias` for the same exact evidence. Q3 asks approval of source collapsing and modalities. No weights, threshold, content filter or negation rule is introduced.
