## B2 analysis (planner extra top-level key): no structural cause found

Evidence (captured bodies, read only): the tool `input_schema` of requests n=8 (edit) and n=31 (ragoff) has `additionalProperties:false` at the top, 15 required properties, all satisfiable: the reply of n=8 carries `scene` and `knowledge_needs` correct and adds `"scene_attributes": []`; n=30 adds `"knowledge_needs_dummy": null` beside a correct `knowledge_needs: []`. Hypotheses tested:
1. *A required property whose allowed values are empty for this request:* generate requests set `maxItems: 0` on `knowledge_needs`, `edit_targets`, `delta`, `preserve`, `dependent_effects`; `[]` satisfies each and the model sent `[]` for them. The edit request allows positions 0..1. Not the cause.
2. *Prompt text naming a field the schema lacks:* `grep scene_attributes|knowledge_needs_dummy|scene_unused|_dummy` over `prompts/`, `contracts/`, `src/`: 0 hits. `planner_v1.txt` says "Knowledge needs", which matches `knowledge_needs`. The prompt never describes `scene` (location, medium, attributes), so a model may flatten `scene.attributes` to a top-level key; this is a prompt-content gap, a guess about model behaviour, not a request defect that the data prove.
3. *Same request, different outcome:* #28/#29 and #6/#7 are byte-identical requests; the second draw was accepted (#29) or failed on another rule. A schema that is unsatisfiable would fail both draws.
4. Tool description is the fixed `Submit the reply object as the tool input.` (`model_cloud.TOOL_FORCED_DESCRIPTION`); the schema's `$comment` names no such key.
**Verdict:** sampling noise of a non-strict tool on Haiku (`strict` is blocked by the grammar limit seen in H1), not a structural defect. Not fixed: a prompt revision would be an unmeasured guess and would invalidate planner-bound evidence; dropping or ignoring unknown keys is a product decision (not done, not proposed here beyond naming it). Options for the PM: measure the rate over more draws, or decide the tolerance.
