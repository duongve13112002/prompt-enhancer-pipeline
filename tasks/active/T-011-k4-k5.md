### Model-facing reply and trust boundary

Proposed new schema ID: `alias_generator_reply.v0`. JSON Schema object with `additionalProperties: false` at each object level; required `aliases` array (empty allowed). Each item requires `text` (nonempty string) and `language` (nonempty string or null). Language/script is the model's stated label, not a code-derived classification or a restriction on user input.

```json
{"aliases": [{"text": "Labelled test alias", "language": null}]}
```

The reply has no concept ID, path, key, origin, status, collisions or revisions. The separate JSON user-data object carries `concept_name`, `descriptions` (deterministic list, possibly empty), `card_summary` and configured `languages`. Load the configured system prompt byte-for-byte. Every supplied string, including descriptions and card text, is untrusted data. Reject unexpected fields, invalid types, invalid Unicode encoding and malformed structures; do not add lexical content filters. Code maps each valid item to the trusted current concept and sets provenance/status. Strings resembling paths, IDs, JSON delimiters or instructions remain literal alias data and never select a path, pipeline identity or metadata key (R-026). The existing table's alias-text PK column is data, not a model-selected pipeline key.

### Questions (ranked, with proposed answers)

1. **Does collision checking include another concept's canonical name, as well as its aliases?** Stage text says two concepts but does not define whether canonical names participate (`K4-aliases.md:10`). **Proposed:** yes; build the collision ownership map from trusted canonical names plus aliases. Only alias rows get pending_review; concepts retain their names. This prevents an alias from automatically competing with an existing canonical name.
2. **If one exact alias text for the same concept is both author-supplied and generated, which origin occupies the single table row?** The table PK permits only one (`tables.py:110`). **Proposed:** author wins the exact-text duplicate; author language stays null, generated candidates remain in their checkpoint. Distinct raw spellings stay distinct rows; normalized forms are used only for collision grouping. No semantic synonym merging.
3. **How should an author-only alias row represent absent model/prompt revisions?** The stored schema currently requires nonempty strings (`alias_set.v0.schema.json:60-72`), while the stage requires a model revision for generated aliases (`K4-aliases.md:5`). **Proposed:** allow explicit null revision fields for author-only provenance; keep nonempty actual model/prompt revisions mandatory for generated rows. Update schema constraints and tests together; do not fabricate a model ID or call merely to fill metadata.

### Proposed index contract, keying and search

**PM decision pending user review:** use an explicit exact-engine contract rather than keep unused ANN/threshold settings. This is a draft configuration migration, not engine selection by experiment. Examples remain non-runnable until fitted/selected values are supplied. No guessed threshold or hidden default.

Build API takes an active `SnapshotBuilder`, explicit config and the snapshot's tables already written through that builder. It verifies the required table entries against supplied table bytes/metadata before trusting them; caller-provided rows cannot substitute for different persisted rows. Required inputs include `concepts`, `folder_concepts`, `aliases`, `cards`, `concept_text_embeddings`, `images`, `image_embeddings` (and reference tables needed by existing catalog checks). Read descriptions from the assigned membership rows; never read source folders, images or info files. Report missing tables precisely before adding index files. Return the content key, manifest path, artifact references, counts and validation result; never call `finish` or `publish`.

All persisted index/cache payloads are Arrow IPC, including a single-row metadata document carried in an Arrow string field; no pickle/object arrays or separate JSON/npy artifact. Proposed generated paths are `index/manifest.arrow`, `index/exact.arrow`, `index/lexical.arrow`, and `index/text-<ordinal>.arrow` / `index/image-<ordinal>.arrow` vector shards, each at most `block_rows` vector rows. Ordinals and schema/layout constants are artifact-bound, never derived from alias text. Storage checks path identities and cross-platform containment. Metadata schema `serving_index.v0` specifies layout, content key, engine, metric, block size, n-gram settings, source table hashes, embedding-space revision/dimension, tool revisions, shard names/row counts/size/checksum and reference schemas.

- **Vector references:** preserve the complete embedding-row PK alongside each vector, and its target concept/image ID. Float32 storage is inherited from K1's table contract. Return embedding-row hits; do not silently collapse several concept texts or introduce S1/S3 aggregation policy. Query supplies explicit positive integer `k` and expected embedding revision/dimension; refuse mismatch before arithmetic. Return at most min(k, eligible rows); an empty catalogue returns an empty result.
- **Scores and ordering (proposed Q2):** explicit metric selects cosine (normalize scratch vectors/query only; refuse zero norm) or raw inner product (zero vectors valid). Compute scores in float64 as a named numerical safety rule over finite float32 source values; preserve stored vectors. Rank by descending score, ties by complete stable row key. Refuse nonfinite/invalid query data and nonfinite computed scores. No approximate search or score cutoff. Check numerical agreement with a scalar reference using an explicitly test-only tolerance; do not promise bit-identical BLAS results across machines.
- **Exact/lexical aliases:** read K4 one row at a time, validating singleton stored documents and raw provenance. Include accepted aliases only; pending_review/rejected aliases never enter exact/lexical serving entries. Names always enter exact lookup, so a rejected competing alias cannot hide the canonical owner. Exclude alias-kind vector rows unless `(concept_id,text_hash)` matches an accepted alias using imported K1 `text_hash`; retain source-vector PKs for every eligible row. This is a safety exclusion, not an instruction derived from text.
- **Exact map:** shared `normalise_name` key to deterministic concept IDs plus source references (concept row or alias PK). Keep all valid owners, never overwrite by insertion order. Own-name checks cover every concept, including short names and concepts without vectors/cards.
- **Lexical map (proposed Q3):** apply shared normalization, then contiguous Unicode code-point windows of configured length, independently to each name, assigned description and accepted alias. Store distinct `(gram,concept_id,source-table,source-PK)` postings; never make grams across field boundaries. No boundary padding, shorter-gram fallback or tokenization. Empty/shorter-than-n text contributes no grams; exact name lookup still works. Query returns candidate concept IDs with distinct matched-gram counts and deterministic ties; no fitted threshold, BM25 or cross-channel score fusion is invented.
- **Content identity/resume:** stream source content hashes, including PKs, relevant text/status/provenance and vector bytes, in deterministic key order. Hash the input inventory plus selected settings, shared normalization implementation revision, K5 code/layout/schema hashes and actual numpy/Arrow versions; keep the embedding-space key in the metadata and query gate. Snapshot ID is binding metadata, not semantic content identity. No source KB path/mtime or transport setting enters the semantic key.
- **Checkpoint units:** use existing writer checkpoints for each content-keyed Arrow shard/lookup output, followed by a complete Arrow metadata checkpoint only after all units validate. Generic checkpoint revision slots explicitly hash source embedding-space identity, structural-stage/no-model-call identity, and schema/tool revisions; do not fabricate model/prompt provenance. Reference reused artifacts through the builder. A failed/interrupted unit never becomes done; an existing durable done artifact is preserved. On rerun verify hashes and payload schema/references before reuse, not just the done flag. A complete repeat on the same builder validates and returns without duplicate `add_file` calls; after partial snapshot-file attachment, abandon that unsealed builder and attach verified checkpoints to a fresh builder. Never edit a sealed snapshot.
- **Validation:** reopen saved files through the storage API/verified building paths; check schema/version, source fingerprint, shard completeness, unique row keys, finite vectors/dimensions/revisions, posting/exact target rows and accepted-alias eligibility. Compare coverage with all eligible source rows so omission of an index entry also fails. Verify each concept's own-name lookup contains its ID. A success report means these checks ran; generic snapshot hashing alone is insufficient.

The numerical and lexical policies above are structural proposals, not measured retrieval quality. Any additional policy uncovered during implementation is recorded as **PM decision pending user review** before use.

### Memory and work bounds

Let N be eligible vectors in one modality, D dimension, B=`index.build.block_rows`, and k explicit requested results. Process one query at a time, one shard of at most B rows at a time; compute `X_block @ q`, select that block's top k by stable ordering, then merge with at most k retained hits. No N-by-N construction or N-by-query-count score matrix. Per query arithmetic is O(ND); sorting costs at most O(N log B) plus bounded candidate merges. Vector scoring workspace is O(BD+B+D+k), independent of N; float32 shard bytes, float64 scratch and transient serialization copies coexist, so `8*B*D` alone is not a peak-memory claim. Float64 matrix/scores use `8BD+8B` bytes, query `8D`, with additional Arrow bytes, indices, candidate keys and library workspace. Check integer products/shape conversion before allocating; allocation failure is an explicit failure, never a smaller hidden block fallback.

Build serializes one vector shard at a time, avoiding a second full dense N-by-D numpy matrix. Source Arrow tables may already occupy O(ND), and exact/lexical postings and metadata occupy O(input text + postings + N references). Existing storage `finish` also loads snapshot tables; P2 does not claim total process RSS is bounded solely by B or repair storage memory behavior. Tests use tiny fixtures and deterministic allocation-shape/count assertions, not machine timing or RSS thresholds. Rebuild/reference validation scans each input once per pass plus emitted postings, not once per concept/query candidate; check cold/cached work at N and 2N.
