### 2. Unknowns and failure modes

### Root cause per class (S31)

- **F, program provenance cannot be proven from text (items 1, 2, 3, 6, 7).** Each finding was a place where a program, or a code-carrying argument, reached git without the guard following that role. Prevention by structure (both modes):
  - Code-carrying roles of shells and wrappers are walked as nested commands that keep their wrapper chain: `Cmd.via` (`shell_targets.py`) lists the programs a command was read from (`bash -c`, `powershell -EncodedCommand` (item 7), `iex`/`eval`/a quoted wrapper word, a script piped into a reader, `find -exec`, and GNU env `-S`/`--split-string` in every spelling, `_split_strings`, item 1). `check_git` refuses git reached through any `via` like a wrapped git call. A substitution `$(...)` runs in the same shell, so it keeps the outer chain unchanged.
  - A program given a program as an argument (`_given_a_program`): an argument naming git, or naming a shell/launcher whose later arguments name git (`chrt -b 0 sh -c "git ..."`, `uv run git.cmd ...`), is refused unless the program is a read-only printer, a configured launcher or an interpreter running a script.
  - One program-name normaliser, `program_stem` (basename, lower case, `.exe/.com/.bat/.cmd/.ps1`, version suffix, `nodejs` = `node`), used by `_names_git` (every git test, also in `_push_reasons`), the launcher rule and `_interp_family` (item 6; item 2's `nodejs -e`, `ruby3.4 -e`).
  - A command that assigns `PATH` or `PATHEXT` (bash prefix, statement, `export`/`declare`/...; PowerShell `$env:PATH =`/`+=`, `Set-Item env:PATH`, `SetEnvironmentVariable('PATH'`) in the same command line as a git call is refused, reads included (item 3). Read from the shell grammar (assignment syntax on the masked text), not from the code's words.
  - Detection at Git itself (worker mode): `cli_worker.py` takes `git_snapshot` before and after each turn (Claude and Codex): every ref of the common Git directory with its object name, the worktree's HEAD (symbolic name and object), and the reflog size of HEAD and each branch. `git_changes` lists every difference; the turn's status becomes `git_history_changed` (sticky until retirement), the changes go to `git_changes` (`status --json`) and to the result file, and the turn exits 1. This is the mechanism for opaque inline code (`'g'+'it'`) and for a shim on a PATH set outside the command.
- **H, one snapshot from check to decision (items 4, 5).** The guard read HEAD and the pushed branch in two git calls; the pre-push check scanned from the branch's upstream. Fix: `_push_source` reads the branch row `for-each-ref --format=%(HEAD) %(objectname) refs/heads/<push_branch>` once (HEAD is on the branch and its tip, in one reading), decides from it, reads again and refuses any difference (item 4). `prepush_check.destination` takes the base from `refs/remotes/<push_remote>/<push_branch>` (`rev-parse --verify --quiet <ref>^{commit}`), refuses a missing ref by name, and requires HEAD on `refs/heads/<push_branch>` at the checked commit; the whitespace and path parts use that pinned base (item 5).

Effective path: a plain target is itself (removing, moving, renaming, `chmod -R` of a parent covers the ledger); a copy or move into an existing directory is `DEST/basename(SOURCE)` (GNU `cp --help` line 4 "Copy SOURCE to DEST, or multiple SOURCE(s) to DIRECTORY"; a wildcard or `.`/`..` source keeps its component, so `src/.` is DEST itself); a destination that does not exist is DEST itself; a destination that receives contents or unknown relative names is DEST itself (new `Target.spread`: `-T`/`--no-target-directory`, `--parents`, every `rsync`/`scp` destination, `Expand-Archive -DestinationPath` through `PsSpec.contents`); an archive or download placeholder (`tar -x -C`, `unzip -d`, `7z x -o`, `curl -O --output-dir`, `wget -P`) is its parent directory with any subtree. `robocopy`/`xcopy` destinations were already plain targets (contents into DEST) and are now compared by containment. `mkdir`/`md` keep no containment rule: creating an existing parent writes nothing below it.
- **M, snapshot against settled ledger (R15).** `turn_git_changes` read the after-state, then waited (`settle`), then compared the old reading, so a reading taken while an orchestrator command was halfway (A to B of A to B to C) met an entry recording A to C. A write that begins during the reread is caught by the same check on that reread (its `start` precedes its first git write, `git_ledger.begin`), so the accepted reading is one during which no recorded orchestrator command ran. One deadline of `git_timeout_seconds` bounds all waits and rereads; past it the turn is judged on the last reading and, when anything is unexplained, the first reason reads "orchestrator Git write(s) <tool_use_id> begun during the turn did not settle within N s (git_timeout_seconds), so the state was judged mid-write" (fail closed). An unsettled write with no unexplained change flags nothing: there is nothing to attribute, and its later changes fall after the final reading.
- Worker processes: the turn's processes have ended before `turn_git_changes` runs. A process the worker left running that writes before the final reading is in that reading and flagged; one that writes after it is not compared by this turn and is inside the next turn's before-reading, so it is never flagged (residual below).

### Newly refused behaviour (PM decision pending user review)

A worker shell write whose effective path is a parent of the ledger directory: copying, moving, renaming or removing `<state>` or any ancestor (also `rm -rf .tmp` when the ledger lies under that `.tmp`); `rsync`/`scp` into such a parent with any source; archive extraction (`tar -x -C`, `unzip -d`, `7z x -o`, `Expand-Archive`) and `curl -O --output-dir`/`wget -P` into such a parent; `cp`/`mv`/`install` with `-T` or `--parents` into it; `robocopy`/`xcopy` into it. Changed: the turn may read the Git state several times and wait up to `git_timeout_seconds` in total; an unsettled orchestrator write is named in the first reason.

### Deviation from the brief (PM decision pending user review)

The brief says a settle timeout flags the turn. Implemented: an unsettled orchestrator write flags the turn, with its reason first, when the reading shows any unexplained change; with no unexplained change it flags nothing. Reason: there is nothing to attribute, the write's later changes fall after the final reading (so the next turn's before-reading holds them), and an orphan pending record (left when another PreToolUse hook blocks after the guard allowed; never pruned, round 5 `Noticed, not done`) would otherwise flag every turn that overlaps it. Pinned by `test_an_unsettled_write_that_changed_nothing_flags_nothing`; the flagging case by `test_an_orchestrator_write_that_never_settles_flags_with_its_reason`.

### Accepted residuals (round 6; PM decision pending user review)

- A worker change made while an orchestrator write command runs is recorded by that command's entry and explained (round 5 residual, decision 89); the sibling case of the new regression therefore writes before the command begins.
- A process the worker left running that writes Git state after the final reading is never flagged (it lies before the next turn's reading). An orchestrator command whose net effect is nothing writes no entry, so a reading of its intermediate state is flagged. A forged entry with a far `end` keeps the loop rereading until the deadline (it only delays, it explains nothing more).
- `rsync` is judged by its destination only (any subtree), so `rsync -a x <parent of the ledger>` is refused even when the source cannot reach it.
