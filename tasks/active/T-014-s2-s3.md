### Model calls (S2 only; S3 makes none in T-014)

- **Main call:** one planner call. `images` is `[('source_image', bytes)]` only for `edit` and only when the role's `image.source` permits it; `generate` sends none.
- **Retry:** an invalid reply (schema or invariant) is retried once with the same request. Second failure: `state: degraded`, `intent_ir: null`, warning `SCHEMA_INVALID`, error code `PLANNER_REPLY_INVALID`; the coordinator (T-015) takes the path without knowledge. HTTP retries stay inside `ModelTransport` (`http.max_retries`).
- **HTTP error, refusal or truncation** (`HTTP_ERROR`, `INCOMPLETE_OR_REFUSED`) and `ModelCallError` (budget `stop`, capability missing): `state: failed`, `PLANNER_CALL_FAILED`; no retry, because the docs grant a retry only for schema failure.
- **Second chance** (`planner.second_chance_rounds`, example 1): for mentions the reply flags `needs_lookup` and leaves `no_match`, one extra S1 lookup per mention text (a new `candidates.lookup_mention`, reusing S1's sources over the same pin), then one more planner call with the extended shortlist; at most `second_chance_rounds` rounds, each with the same one retry. A failed round keeps the earlier plan and adds a warning. Retrieval off: no lookup.
- **Bound per request:** `2 * (1 + second_chance_rounds)` planner calls, plus transport retries; a test counts calls with a labelled double.
- **Budgets/concurrency:** the existing `SingleRunBudgetLedger`/`BackendConcurrency` of the caller's `ModelClientRun`; S2 takes a bound client and never builds its own run.
- **Family pick (decision 15, 69):** code keeps `fits` if any, else `neutral`, else all; picks with `random.Random(seed)`. `seed` is drawn with `secrets.randbits(63)` for `per_request`, or is the configured integer (Q-free choice below), and is recorded in `selections` when `resolution.trace_choice` is true. A `resolved` link is never changed by ratings.

### S3 method as built

Per `resolved` or `family` link with a `concept_id` and role: read its card from the pinned snapshot (`snapshot.read_rows('cards')`, never a new pin). Consider facts only for facets in the IR's `knowledge_needs` for that concept. Leave out with a reason: group not in `scope_matrix[role]` -> `OUT_OF_SCOPE`; bound entity carries a user attribute of the same facet -> `USER_LOCKED`; a `negation` constraint bound to the link's entity -> `NEGATED_BY_USER` for every fact of the concept; `single_observation` and `stable_low_diversity` -> `UNSTABLE` (Q2); `varies` -> named or rated variant, random pick by code, others `VARIANT_NOT_CHOSEN`; then `max_facts_per_concept` and `max_facts_per_request` in `fact_order` -> `BUDGET`. Unfaceted curated statements cannot be scope-filtered structurally, so they are left out `OUT_OF_SCOPE` with `facet: null` [PM decision pending user review]. Fact ids: `fact:` + sha256 of (snapshot, concept, facet, value). Images only for `edit` with `attach_kb_reference_images: true`: greedy coverage over observations (`clear` before `partial`, quality, one per `near_duplicate_group`, single-concept folders first), capped by both image limits, channel `attach`, note built from observation values as data. All text stays data: S3 copies strings, never formats them into instructions.

  - `NEGATED_BY_USER` applies when a ledger constraint has `type: negation` and `bound_entity == link.entity_id`.
- **Variants:**
  - Named variant: the named variant wins.
  - Otherwise, under `context_then_random`: `planner.pick` over the ratings (unrated means all `neutral`), with `planner._seed(base, f'variant:{link_index}:{group_id}')`. The base comes from `resolution.random_seed` (`per_request` gives `secrets.randbits(63)`).
  - Under `omit`: every variant is `VARIANT_NOT_CHOSEN`.
  - The chosen fact keeps `stability: varies` and the variant's `image_ids`. A random pick is recorded in `pack.selections` when `trace_choice` is true.
- **Fact order** under `need_then_support`: link order, then the IR need's facet order, then `support_count` descending, then value code points. The budget is applied in that order: `max_facts_per_concept` counts per `concept_id` across links, and `max_facts_per_request` counts across the whole pack.
- **Fact id:** `fact:` + sha256 of the canonical JSON `[snapshot_id, link_index, concept_id, facet, value]`. A curated statement uses `facet: null` and its text as the value.
- **Images:**
  - Selection runs only for `edit` with attach on. Candidates are the kept facts' `image_ids` whose `images.decode_status` is `ok`, with visibility and quality taken from that image's observations for the fact's (concept, facet).
  - Greedy loop: pick the image that covers the most uncovered kept (link, facet) pairs. Ties go to `clear` over `partial`, then higher quality, then a single-concept folder (from `folder_images` and `folder_concepts`), then `image_id`. Skip an image whose `near_duplicate_group` was already used.
  - Stop at `max_images_per_concept` for each concept and at `edit.max_kb_reference_images` overall.
  - `note` is `json.dumps` of the covered `[{facet, value}]` observation pairs: data, with no prose template.

- **F1 confirmed.** `assembly._registry` hashes the schema files (`assembly.py:46-48`) and then calls `SchemaRegistry(directory)` (`:51`), which reads the directory again (`model_schemas.py:15-22`). A write between the two puts a registry built from other bytes under the digest of the first read. Probe: `CACHE thread` and `CACHE process`: `disk type=integer; cached type=string; cached identity reused=True`. The registry already holds one read per file and its own sha256 (`model_schemas.py:16-22`), so the race exists only because of the second, separate pass.
- **F2 confirmed.** `_select_images` takes the note from every visible observation of `(image, concept, facet)` (`assembly.py:202-211`, `:244`), not from the kept fact. Probe: `NOTE: kept=stripes; excluded=dots; attached note=[dots, stripes]`. The observation row holds a raw value that K3 grouped into card values by model-chosen observation positions (`k3_cards.py:123-127`), so raw values cannot be mapped to card values without text matching. What is structural is the card: each kept fact carries its own `image_ids` (the images supporting that value).
- **F3 confirmed.** The mark is `raises=ModelCallError`, so any such error passes. Probe: an unrelated `ModelCallError('reviewer: unrelated transport failure')` before `compose_model_client` gives `1 xfailed`, exit 0 (the reviewer's surviving mutant, reproduced). The real KBS-F1 failure is the plain `ModelCallError('backend has no verifiable probe cases')` at `model_client.py:302`; it has no code or subtype, and the other `ModelCallError`s are plain messages with a text prefix, which I must not parse.
