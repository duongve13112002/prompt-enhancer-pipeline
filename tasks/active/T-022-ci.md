## Brief header

- **Goal:** the orchestrator can run the test suites on GitHub Actions, on the latest Ubuntu and Windows runners, for a pushed commit. The repository is public only for the run and private again when the run ends, green, red, cancelled or timed out ([docs/ci.md](../../docs/ci.md), decisions 26, 77, 111, 112).

- **Work items:**
  1. **Workflow.** `.github/workflows/ci.yml`:
     - a matrix of `ubuntu-latest` and `windows-latest`;
     - triggered by `workflow_dispatch` only (no `push` or `pull_request` trigger), so a push never starts a run while the repository is private;
     - runs the pipeline suite (`tests/` with `PYTHONPATH=src`) and the tooling suite (`tools/agent-workflow/tests`);

  2. **Visibility-window tool**, a tracked Python script such as `tools/agent-workflow/ci_window.py`, run by the orchestrator only. It follows the six steps of `docs/ci.md`:

     Every value that may vary is profile or configuration, refused when absent (AGENTS.md section 5): the time limit, the poll interval, the workflow file, the branch, the report path. It calls `gh` as a child process with `CREATE_NO_WINDOW` on Windows.

     - a failed final verification, reported loudly;
     - an already-public start, which leaves the repository as found and says so.

### Questions (ranked)

1. **Secret scan.** The project has no scanner. A scanner I write would be an invented pattern list (AGENTS.md section 5). **Proposed:** gitleaks, which scans Git history natively (`gitleaks git`). Pin its version and SHA-256 in the config. The scan covers every commit reachable from every remote ref. It is a system tool, so the user installs it, or approves a hash-checked binary under a Git-ignored project folder (AGENTS.md section 4). The tool refuses when the binary is missing, has the wrong hash, exits non-zero or prints a report it cannot parse. I dropped detect-secrets (pip): it scans working-tree files, not history, and would be a new dependency. **Needs user approval** (a new dependency). Until then, the precondition fails closed, and the tests use a labelled scanner double.
2. **Where the window settings live, and their keys.** **Proposed:** a new `tools/agent-workflow/ci_window_config.json`, validated by `ci_window.py` with the same refuse-on-missing style as `guard_config.py`. Facts already in the repo are reused, not copied: remote and branch from `guard_config.json` `git_guard.push_remote`/`push_branch` (`origin`/`main`, lines 42-43); forbidden prefixes and suffixes from `push_guard`; `git_timeout_seconds`. Owner and repository name come from the remote URL; a URL that cannot be parsed is refused. Keys are in the table below. `run_timeout_seconds` starts as a PM value pending measurement and is refit after the first window.
3. **Tests known to fail.** `tasks/STATUS.md:18` records 10 failures in the **Linux container**, caused by "Windows-specific behaviour: process trees, PID times, links, path separators, PowerShell commands". On Windows the suite is green ("Full suite in main: 3237 passed, 4 skipped", STATUS line 22). Their names were not recorded. **Proposed:** both legs run every test with `fail-fast: false`, with no skip, no `continue-on-error` and no deselect. The Ubuntu leg is expected red in the first window. The report names the failing tests, and the PM opens a fix task. CI is green only when both legs are.
4. **How the dispatched run is tied to the commit.** The ref can only be a branch or tag ("The reference can be a branch or tag name"), and `GITHUB_SHA` is the "Last commit on the `GITHUB_REF` branch or tag". **Proposed:**
   - Just before dispatch, `git ls-remote <remote> refs/heads/<branch>` must equal local HEAD.
   - Run `gh workflow run <file> --ref <branch> -R <owner/repo>`, then take the run id from the URL it prints. The REST 200 response carries `workflow_run_id`, and gh says "The created workflow run URL will be returned if available".
   - If no URL is printed, `gh run list --workflow <file> --commit <sha> --event workflow_dispatch --json databaseId,createdAt,headSha` must give exactly one run created after the dispatch time; otherwise the tool fails and does not guess.
   - Then `gh run view <id> --json headSha,event,status,conclusion` must show `headSha == sha` and `event == workflow_dispatch`. A mismatch means failure, and the window closes.
5. **Exposure scope and placeholders.** **Proposed:**
   - The path check and the secret scan cover the history of every remote ref, read with `git ls-remote`, which writes nothing.
   - A remote ref whose commit is not local is a refusal: I cannot scan what I do not have, and `git fetch` is a Git write.
   - The forbidden prefixes are `push_guard`'s plus `runs`. An exact-path allowlist `ci_window.allowed_tracked_paths = [".secrets/README.md", "models/README.md"]` is checked by path only; the tool never opens `.secrets/`.

### Research evidence (signals)

All quotes are from the installed CPython 3.12.10 HTML docs, `<python install>/Doc/html/library/signal.html` and `time.html` (documented), or from the installed stdlib source (source-verified), or from a probe on this machine (experiment).

- Handler execution point: "A Python signal handler does not get executed inside the low-level (C) signal handler. Instead, the low-level signal handler sets a flag which tells the virtual machine to execute the corresponding Python signal handler at a later point(for example at the next bytecode instruction)."
- Where a raising handler lands: "If a signal handler raises an exception, the exception will be propagated to the main thread and may be raised after any bytecode instruction. Most notably, a KeyboardInterrupt may appear at any point during execution." and the docs' own advice: "applications that are complex or require high reliability should avoid raising exceptions from signal handlers. They should also avoid catching KeyboardInterrupt as a means of gracefully shutting down. Instead, they should install their own SIGINT handler." This is F1's root cause: the window catches `KeyboardInterrupt` and lets handlers raise.
- SIGINT default: "SIGINT is translated into a KeyboardInterrupt exception if the parent process has not changed it"; `signal.default_int_handler.__doc__`: "It raises KeyboardInterrupt."
- Threads: "Python signal handlers are always executed in the main Python thread of the main interpreter" and "only the main thread of the main interpreter is allowed to set a new signal handler" (else `ValueError`).
- Windows table: "On Windows, signal() can only be called with SIGABRT, SIGFPE, SIGILL, SIGINT, SIGSEGV, SIGTERM, or SIGBREAK." Probe: `signal.valid_signals()` here = `SIGABRT, SIGBREAK, SIGFPE, SIGILL, SIGINT, SIGSEGV, SIGTERM`; of the table names, `SIGINT, SIGTERM, SIGBREAK` exist. `SIGBREAK`: "Interrupt from keyboard (CTRL + BREAK). Availability: Windows." `SIGHUP`: "Hangup detected on controlling terminal or death of controlling process. Availability: Unix."
- Sleep with a non-raising handler: `time.sleep` "Changed in version 3.5: The function now sleeps at least secs even if the sleep is interrupted by a signal, except if the signal handler raises an exception (see PEP 475 for the rationale)."
- In-flight child on `KeyboardInterrupt` (source-verified, `subprocess.run`): `except:  # Including KeyboardInterrupt, communicate handled that.` → `process.kill()`; `Popen.communicate` waits `_sigint_wait_secs` first. So today a Ctrl+C during the restore's `gh repo edit` kills that child.
- **Assumptions (not re-read, no network):** (1) on Windows the C runtime maps `CTRL_CLOSE_EVENT`, logoff and shutdown to `SIGBREAK`, and the system ends the process when the console control handler returns (a few seconds at most); since CPython's C handler only sets a flag and returns, console close is in effect a hard kill. (2) A child started with `CREATE_NO_WINDOW` has no handle to our console, so our console's Ctrl+C does not reach it. (3) On Linux, a terminal Ctrl+C or hangup goes to the whole foreground process group, so a `gh` child started without a new session receives it too.

**Design (one mechanism, no OS branch beyond the signal table):**

- `SIGNALS = ("SIGINT", "SIGTERM", "SIGBREAK", "SIGHUP", "SIGQUIT")`, filtered with `hasattr(signal, name)`: the only platform difference.
- `class Deferred` (a context manager): `__enter__` saves the current handlers and installs `self._record`, which only appends the signal number to a list and never raises; `check()` raises `Cancelled(Exception)` at a step boundary when a signal was recorded; `__exit__` puts the saved handlers back.
- `open_window` enters `Deferred` before `pre`, checks it before and after every `gh` write and in the `find_run`/`watch` loops, and runs the restore with the recorder still installed. `interrupts_raise`, `interrupts_ignored` and `Interrupted` go away. `KeyboardInterrupt` stays in the `except` list only for callers (test doubles) that raise it directly.
- `restore` and the run cancel catch `Exception` per attempt.
- `subprocess_runner` and `_git` pass `start_new_session=True` (POSIX: the child gets its own session; Windows: ignored, `CREATE_NO_WINDOW` already applies).
- `main` wraps the `run` path in its own `Deferred`, writes the report first, prints, then exits; a recorded signal is named in the report.
- A non-main thread cannot install handlers (`ValueError` at point 0, before anything is owed): that refuses.
- Dropped alternative: keeping raising handlers and narrowing the gap (installing `SIG_IGN` earlier). A raising handler is still active at some bytecode, so the gap only shrinks (the docs' own warning).

### Questions (at most 3, each with a proposed answer)

1. **Windows console close, logoff and shutdown.** Proposed: classify them with the hard kills (phase 2 session check, the exit-3 fix command), because the system ends the process right after the console handler returns (assumption 1) and a restore needs up to `restore_attempts` × `gh_timeout_seconds`. The dropped alternative, a Windows-only `ctypes` `SetConsoleCtrlHandler` that blocks the system, is OS-specific logic and cannot outlast the system's grace period anyway.
2. **Cancel the run after an interrupt** (today only after a timeout)? Proposed: yes, best effort after the restore, so an abandoned run does not keep using private minutes.
3. **`version_args` as a configured key** per scanner entry, rather than a hard-coded `version` argument. Proposed: configured, because the scanner's `args` are already configured, and a hard-coded argument would tie the generic entry to one tool.
