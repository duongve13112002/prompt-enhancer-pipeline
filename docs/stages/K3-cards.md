# K3 Cards: one card per concept

**Purpose.** Turn per-image observations into one concept card per concept that says, facet by facet, what is intrinsic to the concept, what varies and what the evidence cannot decide, so S3 can hand the writer facts with known reliability (R-010, decision 13).

**Input and output.** `observations`, `folder_concepts`, the descriptions from the info files and `kb_overrides.yaml`, then `cards` (a short card summary text per concept, used by K4 and by the concept-text embeddings of K1 part 2; per concept and facet: observed values, supporting images over images where the facet is visible, a stability label, variant groups with `image_id`s, origin) and a lint report for the admin. Schema: [contracts](../../contracts/README.md).

**Method.**
- **Per concept across all folders (decision 10).** A card aggregates every folder that declares the concept: folders `kimono` and `kimono_donut` (its info file declares `kimono | donut`) both feed the card of `kimono`. An attribute that holds across both folders has more support than one seen in a single folder.
- **Equivalent values** ("long black hair", "black hair, long") are grouped by the `card_builder` model, because deciding that two phrasings mean the same needs meaning, not string rules (R-015).
- **Stability labels [P]**, by the criterion of **invariance under variation**: an attribute that stays the same while background, outfit and view change is evidence of something intrinsic; without variation the card says it cannot tell instead of guessing.

| Label | Condition | Use online ([S3](S3-knowledge.md)) |
| --- | --- | --- |
| `curated` | from an info file or `kb_overrides.yaml` | a checked fact, within its wording |
| `stable` | enough supporting images (`cards.min_visible_images`, `fit_from_gt`), no conflicting value, and variation on other facets | a trait of the concept |
| `stable_low_diversity` | no conflict, but images are near-identical or support/other-facet variation is insufficient | only for facets the role treats as intrinsic |
| `varies` | two or more values | variant groups; the choice follows decision 16 in S2 and S3 |
| `single_observation` | seen in one image only | not used as a fact by default |

- **Never a majority vote.** Many similar images do not make a value canonical, and an accessory not seen does not prove it absent; `varies` keeps every group with its images instead.
- **Executable policy `invariance_v0` (user-accepted, decision 130).** Counts use distinct clear/partial image IDs, including across observation contexts and folders. Several semantic groups give `varies`; one visible image gives `single_observation`. A single group is `stable` only with `cards.min_visible_images`, variation in another model-grouped facet or view on the supporting images, and independent near-duplicate groups. The ratio `distinct near_duplicate_group count / distinct visible image count <= cards.low_diversity_max_group_ratio` marks low diversity; a single independent group cannot establish stability. The required finite [0,1] ratio holds `fit_from_gt` in examples. All other insufficient support/variation uses `stable_low_diversity` with reason lint: this explicitly broadens the original near-identical-only condition. Zero-visible facets assert no value and produce visibility-gap lint. No value is fitted here.
- **Reply boundary.** [card_builder_reply.v0](../../contracts/schemas/card_builder_reply.v0.schema.json) has local facet/observation/curated positions, value/view partitions, a proposed kind, summary and semantic lint. Code checks complete partitions and reference domains, maps positions back to evidence, and writes all stored IDs/counts/labels/revisions. Curated free text stays unfaceted. `cards.variant_groups: false` omits the extra variant projection while keeping minority facet values; `cards.lint_report: false` omits the separate report while retaining card findings.
- **Variation proof.** Variation must be supported across images. Conflicting value/view assignments for one image across observation contexts do not supply that proof; ambiguous image assignments are excluded from the variation calculation, while every minority value remains in its own facet evidence.
- **Recomputed, never accumulated:** a card is rebuilt from the current image list at each sync ([N124](../note/N124-incremental-indexing.md)).
- **Lint report:** a description that contradicts the images; a facet the role needs that no image shows clearly; low diversity (a folder of near-duplicates). The separate report (`cards.lint_report: true`) is part of the `kb sync` result, under `stages.k3` (`lint_findings`), and the snapshot tables store none of it; `kb status` prints row counts only. Each card also keeps its own findings in its `lint_findings` field, which `kb show <concept>` prints inside `card`.
- **Origin.** Every model-generated field carries `origin: generated` and the model revision; the user's names and descriptions are never overwritten. `kb_overrides.yaml` can set a concept type, add aliases, assert facts (treated as `curated`) and suppress facets, without touching images.

**Decisions and configuration keys.** `cards.*`: `cards.min_visible_images` and the low-diversity value (`fit_from_gt`, E16), stability policy version; `vlm.roles.card_builder`; `knowledge.overrides_file`. Grouping keys bind only the ID-free positioned payload and semantic model/prompt/reply-schema revisions: concept name, facet labels, observation values/visibility/views, curated text/origin and suppressed facets. Positions sort by model-visible fields before provenance tie breakers, so changing provenance alone cannot reorder the payload. Unrelated concepts, aliases, type-only overrides, file comments/hashes, HTTP/probe/worker settings, policy/report choices and target snapshot do not force model calls. Exact override hashes remain provenance artifacts. Current evidence IDs/counts/curated folder provenance, kind, stability/variants, findings and target snapshot derive a separate content-addressed card document under its stored schema. Report-only changes leave card bytes and document keys intact ([N126](../note/N126-content-addressed-caches.md)).

**Explicit absence and lint identity.** A null model kind remains stored `kind.value: null`, with `origin: generated` recording the model's abstention and code-owned `KIND_NOT_GIVEN`; it never becomes `other`. The concept table keeps kind/origin unset for absence. A valid human type override supplies the effective kind and suppresses the absence lint. Code prefixes every model-authored lint code with reserved `model:`; unprefixed codes identify code-owned findings. Naming reports/checkpoints also record `SHADOWED_NAME_OVERRIDE` and `FOLDER_NAME_SPELLING_DIFFERENCE`, and K3 includes those in its optional report without sending their pipeline references to the model. A failure while deriving/storing a card cannot demote a committed grouping reply; retries reuse it. Corrupt completed artifacts still refuse.

**Seed retry of a refused card reply (K3-RETRY, decisions 183 and 188; revision `k3-card-3`).** `cards.reply_attempts` is the number of requests one concept may spend on a reply that `parse_card_reply` refuses or the client marks `SCHEMA_INVALID` (`fit_from_bench` in the examples until the seed experiment fits it; `1` keeps the single request). The request is re-sent identical except `sampling.seed`: attempt 0 is the profile's request unchanged, attempt k sends `(vlm.roles.card_builder.sampling.seed + k) mod 2^63`. An integer seed is required when the key exceeds 1, and the role's provider (and the budget-fallback default backend) must map `seed`, or the profile is refused naming both keys. No validator text, earlier reply, fence stripping or relaxed validation reaches a later attempt; `HTTP_ERROR`, `INCOMPLETE_OR_REFUSED`, `BUDGET_EXHAUSTED`, any other `ModelCallError`, `SOURCE_CHANGED` and cancellation are never retried, and a call-time `PARAM_UNSUPPORTED` on `sampling.seed` raises `CONFIGURATION_INVALID`. Retries stay inside the per-concept worker pool (no stage-wide barrier, S46) and count against any granted request budget; attempts restart per run. The grouping key comes from the configured role settings, never the per-attempt seed, so a grouping reply stored on attempt 2 is reused by the next run with no model call. Exhaustion fails the stage as before (`k3: STAGE_FAILED ... SCHEMA_INVALID`): nothing is published and no incomplete card is stored. Evidence: each attempt is `{attempt, seed, code, reply_digest}` (digest of the canonical reply, never its text); the `k3_grouping` bundle carries them with the call records, and after each refused attempt a `k3_call_failure` checkpoint holds them, so an exhausted concept keeps every attempt. `kb gc` removes that checkpoint once it is unreferenced and past `sync.gc.retention`: read it before then. `report['attempts']` gives `allowed` and `used` per concept. A later run of the same concept replaces its `k3_call_failure` checkpoint and repeats the same seeds, so the seed experiment reads the failure rows after each run.

**Compute.** CPU over stored rows plus configured text-only `card_builder` calls for value grouping and lint. `build_cards` returns validated cards/concept kinds, lint and checkpoint references without publishing or opening source files. Reuse grouping independently of target-snapshot stamping; the caller supplies the target snapshot ID. CPU-double verification is recorded in the T-010 task file; no live quality or timing claim is made.

**Audit.** `kb audit --config <profile> --folder-count <n> --card-count <n> --seed <integer>` reads one pinned published snapshot. Counts are required nonnegative integers, zero skips a population, and counts cap at available rows. Only folders with `name_source: model` are eligible; all stored cards are eligible. Sorted populations are sampled without replacement using two independent `Random` instances, seeded by canonical JSON `{"population":"folders","seed":<integer>}` and `{"population":"cards","seed":<integer>}`. Labels are protocol-bound and never passed through Python `hash()`; changing either requested count cannot change the other sample. Printed JSON contains status, snapshot ID, seed, requested/actual counts and sampled folders/cards. It never reads `knowledge.root`, calls a model, opens a writer or publishes. Missing stores stay absent; transient leases are released and newly created empty lease directories removed without disturbing other readers.

**Depends on.** K2.

**Failure modes.** A wrong card is wrong for every request (the E16 audit gates card use in production); value grouping merges two different values; a concept whose folders show different subjects under one name (reported in lint).

**Experiments.** E16 (card and label precision), E9 (leakage counterfactual), E14.

**References.** N124, N126, [N109](../note/N109-evisrag.md).
