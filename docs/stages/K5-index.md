# K5 Index: derived serving index per snapshot

**Purpose.** Build, for each snapshot, the read-only index S1 and S3 query during a request (R-016, decision 19). The index is derived: it can always be rebuilt from the snapshot's tables.

**Input and output.** `prompt_enhancer.k5_index.build_index(builder, config)` reads the new snapshot's already-written `concepts`, `folders`, `folder_concepts`, `images`, `aliases`, `cards`, `concept_text_embeddings` and `image_embeddings`. Descriptions are the assigned membership descriptions. It attaches an exact blocked vector index for each modality, character n-gram postings and a normalized exact name/alias map through the existing snapshot builder. It validates and returns without finishing or publishing the snapshot. The P3 `kb_sync.sync_knowledge` coordinator requires this validated result before finishing and publishing; unchanged completed syncs verify the saved index before reuse (R-016/R-017).

**Method.**
- **Character n-grams** need no word segmentation, so one lexical index serves Vietnamese, Japanese, Chinese and mixed prompts without a per-language tokenizer [A]: no comparison of word segmentation against character n-grams for these languages was found.
- **Rebuilt, not edited.** Each sync derives exact blocked numpy search and character n-gram postings from the new immutable snapshot (decision 134); no all-pairs comparison is made (R-016). Production scale is unknown and may be far above 1,000 folders and 50,000 images (decision 71). E13 must measure rebuild time, memory and query latency beyond that scale before fitting deployment build settings (`fit_from_bench`); engine/metric remain `design_required` and n-gram size `fit_from_gt` in the example lineage.
- **Validation before publish:** every index entry points to a row of the snapshot, and sample queries (each concept's own name) return the concept.

**Decisions and configuration keys.** Decision 134 authorizes numpy exact blocked matrix search; FAISS remains optional and unimplemented. `index.engine` must explicitly select `numpy_exact`, `index.metric` selects `cosine` or `inner_product`, `index.build.block_rows` is a positive native integer, and `index.lexical` requires `kind: char_ngram` and positive integer `ngram_size`. Legacy `index.ann` and `index.exact_search_below_count` refuse with a migration message. Base engine/metric remain `design_required`, build `fit_from_bench`, and n-gram length `fit_from_gt` (E1); dev inherits them. Component and command preflight refuse missing, invalid and unresolved values before index activity. No deployment value has been fitted.

**Query contract.** Construct `ServingIndex(pinned_snapshot, config)` explicitly only when retrieval is enabled (R-009); the caller owns the pin. It verifies saved metadata, source fingerprints and complete entry coverage before serving. `exact(text)` returns sorted concept IDs from canonical names and accepted aliases. `lexical(text)` returns candidates ranked by distinct matched n-gram count, with concept-ID ties. Both share `storage.normalise_name` (NFKC then casefold); code-point windows never cross text fields, have no padding/fallback, and produce no grams when text is shorter than n. Canonical names always enter exact lookup. Pending/rejected aliases are excluded from exact/lexical lookup and alias-kind vector rows. K4 rows are validated as singleton `alias_set.v0` documents, so author/generated provenance is never merged (R-026).

**PM decision pending user review:** `index.build.block_rows` controls new builds and changes their content keys. Readers validate the supplied profile but take the shard layout from the snapshot's validated `serving_index.v0` metadata, so a B=1 snapshot remains readable under a B=3 build profile. Engine, metric and lexical settings must still match; missing or invalid profile values and malformed saved layouts refuse.

`search(table, vector, k=..., embedder_revision=..., dimension=...)` returns embedding-row hits with complete primary keys, descending score and stable key ties. It has no aggregation, fusion, cutoff or implicit k. Query space must match K1's stored embedding-space revision/dimension. Cosine normalizes scratch values and refuses zero vectors; inner product accepts them. Stored vectors remain float32, with named float64 accumulation for numerical safety. Floating-point results are checked against a scalar reference with test-only tolerance; cross-machine bitwise reproducibility is not promised. Within one runtime a row's score does not depend on its shard (K5-TIE): each row is scored by a row-wise product and sum, never a BLAS matrix-vector product, whose rounding varies with shard shape and row position, so identical stored vectors tie exactly and break on the primary key.

**Files and resume.** All payloads are Arrow IPC: `index/manifest.arrow` carries the `serving_index.v0` metadata document, `exact.arrow`/`lexical.arrow` carry source-referenced postings, and `text-<ordinal>.arrow`/`image-<ordinal>.arrow` carry at most `block_rows` vectors. Paths come only from the layout. Content keys include source contents, settings, the normalization rule, the declared `K5_INDEX_REVISION` (stored as `tools.code` and guarded by `tests/test_stage_revisions.py`), the schema, the Unicode database version and actual numpy/Arrow revisions. Verified per-unit checkpoints are reused; completion is committed after saved units validate. Complete repeats on the same builder make no duplicate attachment; partial attachment requires a fresh builder and reuses intact unit checkpoints. No sealed snapshot is edited.

**Compute.** CPU only in P2. A single query visits one vector block at a time, using O(BD+B+D+k) scoring workspace for block rows B, dimension D and explicit k; it never allocates an all-pairs score matrix. Source tables, lookup postings and metadata remain proportional to catalogue size, and existing storage validation may hold source tables in memory. There is no claim that total RSS is bounded by B. Performance and deployment scale remain unmeasured; E13 must measure them before choosing production values.

**Depends on.** K1, K3, K4.

**Failure modes.** An index built from a different embedder revision than the query encoder (prevented by keying); a large image index that does not fit memory (`fit_from_bench`).

**Experiments.** E1, E4, E13 (lookup latency under concurrency).
