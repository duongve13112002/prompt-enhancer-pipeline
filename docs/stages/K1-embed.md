# K1 Embed: images and concept text

**Purpose.** Give every image and every concept a vector, so K2 can group near-duplicates and pick representatives, S1 can find concepts described indirectly, and S3 has a fallback for attributes outside the facet schema. Embedding every image (part 1) is the cheap first tier of indexing ([K2](K2-observe.md)).

**Input and output.** K1 has two parts. Part 1 (after K0, before K2): new or changed `image_id`s from K0. Part 2 (after K3 and K4): the text of each concept (name, description, aliases from K4, card summary from K3). Output: `image_embeddings` and `concept_text_embeddings` as Arrow, each row keyed by content plus embedder revision (R-016, R-017). Image metadata (format, dimensions, decode status) goes to `images`.

**Method.** Part 1: decode each image once, record dimensions, embed with the configured embedder; the embeddings group near-duplicates, and those groups let the naming step of [K2](K2-observe.md) choose a varied subset of a folder without an info file. Part 2: embed concept text, which includes the card summary and aliases and so waits for K3 and K4, with the same encoder so text and image vectors share a space. Concept text is re-embedded when the name, description, aliases or card summary change.

Online, S1 embeds only short text (the prompt and its segments), so image embedding never runs on the request path. One embedding space per snapshot: vectors from two embedders are never mixed.

**Decisions and configuration keys.** `embedding.*`: the backend (`embedding.backend` names a local `vlm.backends` entry with an `endpoints.embeddings` route; its `model.revision` must equal `embedding.revision`, `pin_required`), the request layout (`embedding.request.shape`, `image_instruction`, `extra_body`, `text_template`, `design_required` until the live smoke proves them, T-008), the dimension and how it is reached (`embedding.dimension`, `fit_from_gt`, E5; `embedding.dimension_mode`: `native`, `request_field` or `client_prefix_l2`) and the batch size (`embedding.batch_size`, `deploy_required`). Devices are not a client key: the embedding server's launch places the model (`runtime.gpus`, `runtime.vram_budget_gb`, the `gpu-live-run` plan; T-008 Q2). Images travel as data URIs (`vision.transport: data_uri`, the only accepted value). Every image goes through the shared client-side resize of `vision.max_image_side` before embedding (`none` by default, decision 84, [VLM_CALL_RULES](../rules/VLM_CALL_RULES.md) rule 7). The embedder is chosen by E5 on the user's knowledge base, not from published leaderboards, because published figures are measured on other data. Candidate embedders, their licences and their text-length limits are in the references.

**Implementation (T-008).** `prompt_enhancer.k1_embed`: `embed_images` (part 1) takes the K0 handoff, reads each image read-only with no link on any path component and checks its bytes against `image_id`, decodes it once (format and pixel size of the stored file before any orientation go to `images`; a TIFF gives its own size tags), prepares it with the shared resize and embeds it in batches over HTTP. `embed_concept_texts` (part 2) is the interface K3 and K4 will call; it is tested with fixtures. Each input is one checkpoint artifact keyed by its content hash plus the embedder revision, the request settings and the image settings; a rerun skips finished keys, and an artifact a live snapshot references is reused (`REUSED_REFERENCED`) rather than recomputed, because server output is not guaranteed bit-identical. Refusals of an image by policy are stored (`decode_status`); unreadable or changed sources and HTTP or response errors fail the item and are retried at the next sync. Any error the decoder raises on a file's bytes makes that image `undecodable` (stored, not retried); a settings or encoding fault stops the stage. Before any read or request, both entry points check every key K1 reads against that key's node in the configuration schema, with exact integers and finite numbers, the same check `kb sync` runs at load; each timer must also convert to a finite float (the AnyIO and asyncio clocks raise on the rest), and `vision.format` must name an encoder installed in Pillow, used as given with no fallback to the source format, that registers an `image/` media type (`Image.MIME`); the data URI states that registered type, not the encoder name (JPEG2000 is sent as `image/jp2`), and the loader and both standalone entry points refuse an encoder without one before any read or request. K1 returns its tables and never publishes.

**Embedding server (T-018, decisions 137 to 139).** `python -m prompt_enhancer.embed_server serve --config <profile> [--overlay <file>] [--project-root <dir>]` serves the `openai_input_content` request K1 already sends (`/v1/embeddings`, plus `GET` health) from the model's original weights through `transformers`, in the separate GPU environment `.venv-gpu` ([dependencies](../dependencies-and-environments.md)); K1 is unchanged. It serves the backend `embedding.backend` names, which has `engine.name: embed_server` and a `vlm.backends.<name>.server` block (`family`, `dtype`, `attn_implementation`, `forward_batch`, `max_length`, `image`, `default_instruction`, `idle_exit_s`, `max_request_bytes`, `max_image_bytes`, `max_pending_requests`, `max_connections`, `max_discard_bytes`, `read_timeout_s`); host and port come from `base_urls[0]` (plain http, IPv4 loopback or `localhost`, explicit port; IPv6 is refused because the server binds one IPv4 socket), the GPU from `runtime.gpus` (exactly one) and its memory cap from `runtime.vram_budget_gb`. Families: `embedding_gemma2` (mean pooling, L2, no system instruction, never `float16`) and `qwen3_vl_embedding` (last-token pooling, L2, a system instruction from the request or `default_instruction`); the native size is read from the weights' own `config.json`. Before any weight is read, every file of the model must match the runtime manifest `models/manifest.json` ([model-storage](../model-storage.md)) in size and SHA-256 and no unlisted file may lie beside them; `trust_remote_code` is always `False` and a `config.json` with `auto_map` is refused. Images arrive as `data:` URIs only (safety-bound: the server never fetches a URL) and are decoded in the server process by Pillow restricted to `PNG`, `JPEG`, `WEBP`, `GIF`, `BMP` and `TIFF` (`protocol.ALLOWED_FORMATS`, safety-bound; checked from the bytes before the pixels are loaded); the detected format must be the one the data URI's media type names, so a `vision.format` outside that set is refused at start for this engine. The audit of the installed Pillow found one decoder that calls out on load, EPS (Ghostscript with temporary files, `PIL/EpsImagePlugin.py`), and none of the allowed ones does on a normal load (`subprocess` in the GIF and JPEG plugins is in save helpers and in `load_djpeg`, which nothing in Pillow calls); a test spies on process and temporary-file creation. A connection has `read_timeout_s` in total to deliver its request (one deadline, not a per-read timeout, so a client that trickles bytes is cut at the deadline with 408 or a closed connection; the same value bounds the reply send). At most `max_pending_requests` POSTs are admitted at once: a slot is taken after the headers and before the body is read and is held until the reply is sent, so the body bytes, the decoded images and the wait for the GPU are all bounded; a request beyond the bound gets 503 `overloaded` and its body is never read into memory or decoded. After any reply the server half-closes and discards the unread part of the declared body (never stored; at most `max_discard_bytes` whatever length the client declares, and within the deadline), so a refusal (404, 405, 411, 413, 503) reaches the client on Windows, where closing with unread input resets the connection and loses the reply; beyond that budget the reply is best effort. `max_discard_bytes` is at least `max_request_bytes`, so the 413 of an ordinary oversized body can still be drained. The server owns its connections: at most `max_connections` accepted sockets with their handler threads exist at once (at least `max_pending_requests`), the check comes before a thread is created, and an over-cap connection, a health probe included, gets one best-effort 503 `overloaded` written by the accept thread and is closed without a thread (a client that had already sent its request may see a reset instead); every connection ends within its deadlines unless its request sits in the engine. Connection errors and engine errors are logged once per kind and counted, with one summary line at shutdown. All server output (the ready line, the log, the summary) goes through a bounded queue that one daemon thread writes (`server.BoundedOutput`, at most `OUTPUT_QUEUE_LINES` = 64 lines waiting, safety-bound), so no server thread waits for a console or pipe nobody reads; lines past the queue are dropped and counted (`dropped_lines` in the summary). Stop order: new requests and connections are refused (503 `stopping`), the accept loop is asked to stop (the server owns its loop, which looks at a stop event every 0.1 s; the stdlib `shutdown()` waits for its loop with no timeout) and its thread is joined within `read_timeout_s`, the listening socket closes, requests already past their body read (decoding, queued for the GPU, in the engine, replying) get up to `read_timeout_s` to finish while a client still sending its body is not waited for (a request queued behind a running forward is refused when it gets the lock), every blocked read ends within 0.1 s (`CANCEL_POLL_S`, the slice of a receive: shutting a socket down does not wake one on Windows) and every accepted socket is shut down, handler threads are joined within a second `read_timeout_s`, still-registered sockets are closed, and only then is the engine closed, while holding the GPU lock so no forward pass runs under it, on its own thread joined within `read_timeout_s`; the output then gets one more `read_timeout_s` to deliver; a stop succeeds only when the accept thread is joined, the listener is closed, no handler thread is alive, no socket is registered, no request is still admitted and the engine is closed; a survivor (a forward pass that cannot finish leaves the engine open, a handler still decoding or replying) is named in the message and the process exits with status 3 (the exit frees the GPU); output that could not be delivered is not a survivor (it holds no server resource). Every step of a stop is bounded, so a stop takes at most `5 * read_timeout_s` (accept join, grace, handler join with the GPU lock, engine close, output), usually about the grace and the join; the command's last line on stderr gets one more `read_timeout_s`, so a full stderr pipe cannot hold the exit status. No step of the stop raises past the next one: a closing thread the OS refuses leaves the engine open as a survivor (status 3, never a synchronous close), an output writer the OS refuses counts its lines as dropped and never changes the status, and once the profile is read any unexpected error becomes one line `failed: <type>` on stderr and status 1 instead of a Python traceback; before the profile is read (`argparse` usage and errors, a configuration refusal) nothing is owned and the line is written directly. Requests run one at a time on one GPU lock; `/health` answers `loading` (503) until the weights are in; the server exits on a signal or after `idle_exit_s` seconds without a request (`0` never exits); a stop signal or the idle timeout is noticed within 0.5 s (the poll period of the server loop), so the exit comes up to 0.5 s after `idle_exit_s`. Status: the request path, configuration, manifest check and lifecycle are tested on the CPU with a labelled engine double; `server.max_length` cuts a text input in the tokenizer (both families) and refuses an image input that needs more tokens (an image is never cut); K1 folds the settings that change vectors (family, pooling, dtype, attention kernel, `max_length`, image limits, `default_instruction`) into the embedding-space identity for this engine only, so a changed setting re-embeds and a transport or batching value (`forward_batch`, byte limits, timeouts, admission bound, GPU) does not; the model adapters in `embed_server/models.py` are written from the model cards and `transformers` v5.23.0 source and are **not yet run**: the reference check against each card's sentence-transformers output (P2) decides them.

**Compute.** GPU on the dev machine and the deployment, batched; the embedder can share the GPU with the serving model only within the VRAM budget of [PLATFORM_GPU_RULES](../rules/PLATFORM_GPU_RULES.md). Nothing measured; the live smoke is a separate `gpu-live-run` step.

**Depends on.** Part 1: K0. Part 2: K3 and K4.

**Failure modes.** Text longer than the encoder's token limit is truncated silently (check per encoder); weak coverage of a language or script in the encoder (measured in E1 and E5 per language and script); a changed embedder without a new index (prevented by keying on the revision).

**Experiments.** E5 (embedder comparison), E1 and E4 (contribution of dense search to linking).
