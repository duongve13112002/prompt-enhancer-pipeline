# S6 Envelope: status, output, attachments, trace

**Purpose.** Return one response with an honest status, the output exactly as the admin profile's contract defines it, and everything else outside the output (R-024).

**Input and output.** The checked output and status from S5, the Knowledge Pack's `attach` images, the source binding, the retrieval state, then the response envelope ([contracts](../../contracts/README.md)) and one `request_traces` row.

**Method.**
- **Envelope fields:** `status`; `output` (verbatim per the profile contract); `attachments` (per image `image_id`, role `knowledge_reference`, the entity it binds to, the facets to use; images are copies from the snapshot, never from the source tree); `source_binding` (the source image's `image_id`); `retrieval` with `state`, the pinned snapshot and `error`; top-level `warnings`; `trace_id`. Schema `response_envelope.v1` (T017-FIX3, decisions 198 and 200); `response_envelope.v0` stays for stored envelopes.
- **Warnings** use the `response_envelope.v1` enum, including `VERIFIER_UNCALIBRATED` for permitted inline verification without matching evidence. Trace metadata uses deduplicated warning codes and keeps span-bearing warnings in their stage records. The output remains the profile payload.
- **Status** comes from S5, or `needs_clarification` from S2 when `clarification.mode` is `ask` and an edit target is ambiguous (with the candidate targets) or `resolution.on_family_match` is `ask` and a mention is a family match (with the candidate concepts). With `best_effort` (the example value, decision 68) no request ends in `needs_clarification`: the most plausible reading is written with status `degraded` and the reason in the trace.
- **Retrieval state [P]:** `disabled` when `rag.enabled` is false; `skipped_no_knowledge_needed` when the planner lists no knowledge need; `no_match` when no mention resolved to a concept, or concepts resolved but no fact passed the filters; `retrieved` when at least one fact or image was assembled (definitions: [contracts](../../contracts/README.md#enums)); `failed` when a knowledge access failed, the snapshot was missing included; `not_reached` when retrieval is on, nothing failed and S3 did not run (an S0 refusal before the knowledge boundary, a failed or clarifying plan), so a run that never reached retrieval is not reported as a failure or as `no_match` (decision 200).
- **Retrieval error [P] (decision 198):** `retrieval.error` is `null` unless the state is `failed`, and then exactly one closed code, never stage text (R-026), checked in this order: `SNAPSHOT_MISSING` (no published snapshot), `KNOWLEDGE_FAILED` (an S0 knowledge refusal), the S1 shortlist's own code (`WINDOW_BUDGET_EXCEEDED`, `RETRIEVAL_FAILED`), `RETRIEVAL_FAILED` for an S2 lookup failure, then the S3 assembly's code (`KNOWLEDGE_READ_FAILED`).
- **Trace** records the configuration hash, profile and addendum versions, `snapshot_id`, shortlist, Intent IR, resolution decisions, Knowledge Pack, executed brief, ledger verdicts, repairs and timings. It records both configured role model IDs even when a role is skipped or falls back. Call records identify the actual routes.

**Status precedence.** A fatal deadline or S0 refusal fails with null output. A valid ask-mode clarification returns null without S4/S5 calls. Unusable output fails. Usable output remains degraded after upstream degradation, failed retrieval, best-effort ambiguity or S5 fallback. Otherwise S5's checked first draft succeeds, and a checked repair is `repaired`.

**Library lifecycle.** `Pipeline` exposes `enhance`, response `after_delivery`, and `close` or async context management. It reserves trace capacity before generation. `runtime.trace.workers` bounds executor workers for trace writes and maintenance. The repository serializes segment appends under its lock. A selected monitor runs only after acknowledgement of the eligible checked output, makes one calibrated verifier call and leaves the delivered envelope unchanged. Closing joins active requests and all delivery cleanup, including capacity-skipped and unacknowledged tickets. `GoldenAdapter` (`s0-s6.v3`) runs the same coordinator with the confirmed view and snapshotted writer brief; each case's `request.retrieval` selects the pipeline: `enabled` the given one (which must have retrieval on), `disabled` one with `rag.enabled: false`, a second owned `Pipeline` when the deployment has retrieval on, so that case opens no store and runs no S1, S3 or K stage (decision 197, R-009). T-016 owns transport delivery hooks.

**Retention and attachments.** `kb sync` retains a hash-checked copy of every distinct scanned image in the snapshot (`images/<sha256>` plus a layout marker; [K0](K0-sync.md)). With `edit.attach_kb_reference_images: true`, intake refuses before S4 a pinned snapshot without that layout or with an entry missing or of the wrong size, and the pipeline re-reads and hash-checks the selected `attach` images (at most `edit.max_kb_reference_images`) right after S3; both refusals use `KNOWLEDGE_FAILED` and name `kb sync`. With no published snapshot the request degrades (`SNAPSHOT_MISSING`) and attaches nothing. The envelope's bytes come only from the pinned snapshot, never the source tree. The attachment path requires a successful hold before releasing a request lease. Trace and hold expiry must be representable before persistence. Maintenance indexes trace history once per lifecycle and removes expired segments through anchored storage. Closed services process expired rows on restart. A trace drain timeout is diagnostic and in-flight OS writes are joined.

**Decisions and configuration keys.** Positive finite `runtime.request_deadline_s`, `runtime.trace.retention_s`, `runtime.trace.drain_timeout_s`; positive integer `runtime.trace.queue_limit` and `workers`; conditional positive-sampling `runtime.monitoring.queue_limit`, `workers`, `drain_timeout_s`; existing `storage.data_root`/format and attachment-only KB hold settings. Examples retain unfitted sentinels, with explicit startup refusal when consumed.

**Compute.** CPU; durable trace writing is submitted without awaiting disk I/O on the response path. CPU tests use labelled doubles; live behavior and performance remain unmeasured.

**Depends on.** S5.

**Failure modes.** A status that hides a degradation (each status has a test, R-024); attachments that point at a collected snapshot (prevented by retention while traces reference it); traces that carry personal prompt text beyond retention (`deploy_required`).

**Experiments.** E13 (end-to-end latency and throughput).

**Several source images (designed, not yet implemented; MS-5).** A request sent as `request.v0` still gets the envelope of today's path (`source_binding`; `response_envelope.v0`, or `response_envelope.v1` from T017-FIX3). A `request.v1` gets `response_envelope.v2`, written by MS-5 on top of `response_envelope.v1`: `source_bindings: [{index, source_image_id}]` replaces `source_binding`, and each `attachments[]` entry gains `index`, its reference number counted from 1 in `attachments` order, so the order is explicit and not implied by array position. The enhancer renders nothing; the caller sends the sources and the references to the image model by `index`. Trace rows gain `body.contract_versions` and `n_sources`; older rows without them are v0 by definition and are never rewritten. Contracts: [contracts, multi-source section](../../contracts/README.md#multi-source-contracts-designed-not-yet-implemented).

**References.** None beyond the contracts.
