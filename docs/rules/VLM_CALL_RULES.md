# Model call rules (binding detail of AGENTS.md)

Read before changing a prompt, a model call, the client or the backend settings. Request fields: [contracts/vlm-request.md](../../contracts/vlm-request.md); prompt contract: [prompts/README.md](../../prompts/README.md). Rules and source name no model: models and backends are profile values (R-018).

1. **Backend.** Every model role (`vlm.roles.<name>`) is reached over HTTP through its configured backend. The repository never installs or starts a production server. Keys live in files under `.secrets/`; a non-loopback endpoint uses HTTPS. Record provider, endpoint name (not the key), model id and revision with every run.
2. **Capability probe.** Send demanded challenges with the requesting role's mapped reasoning, sampling, token limit and image policy through the same builder as real calls. Cache proof only for an identical request-shaping context, including resolved output schema and effective backend; contexts share one backend/run allowance, including retries. The result is stored with the run ([dev-machine](../dev-machine.md), E12). Strict deterministic reply checks prove instruction following under the sent settings. Request acceptance does not prove that thinking/sampling controls have their semantic effect, or that the server enforces `response_format`; independent control evidence and post-engine validation remain required. Failed proofs retain closed truncation, refusal, malformed or wrong-answer codes in diagnostics; model text stays out of errors. **Seed retry of the plain `image` challenge (decision 188).** Only that challenge, only a reply refused as `PROBE_MALFORMED` (a verdict `PROBE_WRONG_ANSWER`, a transport failure or a truncation is never retried): it is sent again identical except `sampling.seed`, up to `vlm.backends.<name>.probe.image_attempts` requests in all (a sentinel until the seed experiment fits it; `1` keeps one request). Attempt 0 uses the role's own seed; attempt k sends `(seed + k) mod 2^63`. Every request, retry included, is taken from `probe.max_requests`; the profile loader refuses an `image_attempts` the allowance cannot pay when the role's own challenges are counted, naming both keys, and a retry the allowance cannot pay at run time leaves the challenge `PROBE_INCOMPLETE`, never negative. The proof is `negative` only after every attempt failed, and each attempt (index, seed, code, reply digest, never the text) stays in the event's `challenges[*].attempts`, passed or failed. The `text` and `multiple_images` probes are not retried (see `tasks/active/K3-RETRY-seed-retry.md`, Noticed, not done).
3. **No implicit defaults.** Every request field is stated in the profile; none is left to a library or server default.
4. **Thinking off on the request path** where the backend allows it; the switch name is a profile value ([serving](../serving.md), E10).
5. **Unsupported parameters** are dropped with a recorded `PARAM_UNSUPPORTED` warning, and the effective request is stored, so every result stays bound to what was really sent.
6. **Prompt versioning.** Every prompt has a `prompt_id`. A change is a new id and invalidates every fitted value that depends on it, because fitted values belong to one (model, prompt, image size) combination.
7. **Image size (decision 84).** Every image sent to any model (VLM roles, image embedder) goes through one client-side resize: `vision.max_image_side: none` sends the original; an integer N downscales so the longer side is N, keeping the aspect ratio, never upscaling. A role may override it with `image.max_side`; a chat call uses the smaller of that side and its backend's `vlm.backends.<name>.image.max_side` (decision 144; `none` = no backend limit; embedder backends keep `none` until K1 includes it). Experiments and benchmarks use 1024; with a cloud backend the cap also bounds the cost, because image tokens grow with pixels.
8. **Data, not instructions.** Knowledge-base text, text read from images and captions go in as delimited data, never at an instruction position (R-026, [N131](../note/N131-image-prompt-injection.md)).
9. **Structured output** is validated after the engine, because engines may ignore schema keywords silently. An invalid response is recorded (`SCHEMA_INVALID`), retried only as the stage design allows, and never repaired by guessing. The K2 observer and the K3 card builder retry a refused reply with another seed (decisions 183 and 188): the request is identical except `sampling.seed`, no validator text or earlier reply is added, a retry counts against any granted request budget, and an `HTTP_ERROR`, `INCOMPLETE_OR_REFUSED`, budget or cancellation failure is never retried ([K2](../stages/K2-observe.md), [K3](../stages/K3-cards.md)).
10. **Independence.** Evaluation, labels and test scenarios are never judged by the model that produced them. The runtime verifier is the exception (decision 153): choosing a verifier model different from the writer is the admin's responsibility; the product does not refuse or degrade a request when both roles resolve to the same model (a renamed deployment of one model cannot be detected), and the trace records both configured model ids.
11. **Cloud backends and budget (decision 28).** The local backend is the default for every role. A cloud backend (Claude or Gemini; the default model ids are profile values in `configs/enhancer.example.yaml`) is used only when the configuration profile binds a role to it, its key file is under `.secrets/`, and the user has said how many requests it may spend (`call_budget: ask_user` until then). Count every call against the budget; when it is spent, continue on the default backend with the warning `BUDGET_EXHAUSTED` unless the profile says `stop` (decision 29). Images go to a cloud provider only while `allow_images` is true; when it is false, a request that carries an image runs on the default backend.
12. **Claims.** State no accuracy or throughput number for a model without a note (R-021); measure on the user's backend.
13. **No word lists.** No per-language rules or keyword lists in prompts or code; meaning comes from the model, structure from direct checks (R-015).

**Where model names may appear.** The rule that rules and source name no model (R-018) is about the product's models. Their names appear only in example profiles and overlays under `configs/`, in [dev-machine.md](../dev-machine.md) and [serving.md](../serving.md), in research notes and in the decision record. The agent models in `.agents/policy/PM_POLICY.md` are a separate matter: they are the tools that build the product.
