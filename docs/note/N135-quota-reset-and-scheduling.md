## What this project relies on

- **Claude Code, in-session scheduling.** `CronCreate` takes a 5-field cron expression in local time, recurring or one-shot; a one-shot can be pinned to a minute and hour. "Tasks only fire while Claude Code is running and idle. Closing the terminal or letting the session exit stops them firing." "A session can hold up to 50 scheduled tasks at once." Recurring tasks expire after 7 days; one-shot tasks do not. One-shot tasks on minute :00 or :30 may run up to 90 s early, so pick another minute. A missed fire is not caught up. Resuming a session "restores the tasks scheduled with CronCreate, except recurring tasks that have expired and one-shot tasks whose scheduled time has passed". `CLAUDE_CODE_DISABLE_CRON=1` disables them. No Windows limitation is stated, and none is confirmed either.
- **Claude Code, reset times for scripts.** The status-line command receives JSON with `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` (0 to 100) and `rate_limits.five_hour.resets_at`, `rate_limits.seven_day.resets_at` (Unix epoch seconds); "appears only for claude.ai Pro, Max, and Ultra subscribers ... only after the first API response in the session ... Claude Code drops a window once its `resets_at` time passes." The SDK stream documents `rate_limit_event` with `rate_limit_info.status` (`allowed`, `allowed_warning`, `rejected`) and `resetsAt`; that `claude -p --output-format stream-json` carries it, and the unit of `resetsAt`, are not stated.
- **Claude Code, the PM's own limit.** Interactive sessions can wait for a usage limit to reset and then continue: "Claude Code waits in the open session and continues the task on its own after the limit resets ... Requires Claude Code v2.1.234 or later"; at most 3 automatic continuations; setting `autoContinueAtUsageLimit`. The `claude -p` limit message gives a local clock time without date ("You've hit your session limit · resets 3:45pm"), so it is not parsed for scheduling.
- **Claude Desktop (read by a fetch agent on 2026-11-13; some lines are its summary, not verbatim).** `autoContinueAtUsageLimit` is described only for interactive terminal sessions ("Wait in the open session and continue the task automatically after a claude.ai usage limit resets", settings reference; set in `/config` as "Continue automatically at usage limit"; on by default for subscription sessions per the interactive-mode page summary); the Desktop page names no equivalent, and the user found none in the app. `CronCreate` and `/loop` are described for CLI sessions; Desktop support is not stated. **Desktop scheduled tasks** (https://code.claude.com/docs/en/desktop-scheduled-tasks): Code tab, Scheduled, New task, "Only on this computer" with a local folder, Desktop 1.1.5368 or later; "Scheduled tasks start a new session automatically at a time and frequency you choose"; "Tasks only run while the desktop app is running and your computer is awake"; asking Claude "remind me at 3pm tomorrow ..." creates "a one-time task that disables itself after it fires"; "You can also list, create, edit, and pause tasks by asking Claude in any Desktop session" (an `update_scheduled_task` tool asks for approval on each call); one catch-up run for the most recent missed time; "Allow rules from `~/.claude/settings.json` also apply to scheduled task sessions." The desktop app reads the same settings files as the terminal (settings page).
- **Claude Code, waking from outside.** `claude -p --resume <session_id>` continues a session non-interactively, but "If you resume the same session in two terminals without forking, messages from both interleave into one transcript"; it is not used on a running PM session.
- **Claude Code, cache and effort.** Quoted by a research agent from the prompt-caching page: "With an API key or a Claude subscription, changing effort keeps the cache on Fable 5.1 and later, Opus 5.5, Sonnet 5.5, and Haiku 5.5."
- **Codex.** `TokenCountEvent.rate_limits` holds `primary` and `secondary` windows with `used_percent`, `window_minutes` and `resets_at` ("Unix timestamp (seconds since epoch) when the window resets"); `TokenCount` events are persisted in the session JSONL files under the Codex home. The `codex exec --json` stream carries no rate-limit field. The limit error appends " Try again at {formatted}." in local time (no date on the same day), so it is not parsed for scheduling. Limits can be per feature (ids such as `image_gen`).
- **Antigravity.** Paid plans have a quota "refreshed every five hours until the weekly limit is reached". `agy -p /usage` produces a text report, not JSON: "Slash commands that the CLI can respond to directly (such as /model and /usage) produce a text report rather than a standard event stream." The status-line JSON has a `quota` object per bucket with `remaining_fraction` or `remaining_amount`, `reset_time`, `reset_in_seconds`. The exhaustion error text (`RESOURCE_EXHAUSTED`, "Resets in ...") is not in the official docs.

## Re-read 2026-11-15 (T-026; Claude Code 2.1.325, agy 1.5.9 on the dev machine)

- **Status line (Claude Code).** Confirmed the fields above. New: a third window `rate_limits.spend_limit` behind a Claude apps gateway. Updates are debounced at 300 ms, an in-flight script "is cancelled" by the next update, and the command re-runs when a window reaches its `resets_at`. "On Windows, Claude Code runs status line commands through Git Bash when Git Bash is installed, or through PowerShell when Git Bash is absent" (forward slashes in the path). Neither the status-line page nor the Desktop page says that **Claude Desktop** runs the status line; the Desktop page names only "the usage ring ... Click it to see your plan usage". Treated as: Desktop does not run it (unknown).
- **`rate_limit_event` (experiment).** Units are still undocumented. Live worker turn logs (`.tmp/cli-jobs/*/NNN.jsonl`, 65 events in 42 logs) carry `resetsAt` 1795010400 = 2026-11-18T14:00:00Z, the weekly reset Claude Desktop showed, so it is **epoch seconds**; `utilization` rose 0.08 to 0.15 over one day, so it is a **fraction 0..1**. The events also carry undocumented `rateLimitType` and `unifiedWindows` (per-window `utilization`, `resetsAt`, `status`); every event seen names only `seven_day`.
- **Structured `/usage` (Agent SDK).** Sending `/usage` as a prompt returns `usage_report` with `rate_limits.limits[]` (`kind` such as `session`, `weekly_all`, `weekly_scoped`; `percent` 0-100; `resets_at` ISO 8601) for claude.ai credentials. The `claude -p /usage` probe was not run, so whether it starts a model turn is unknown.
- **Antigravity status line.** `quota` "Maps quota bucket IDs to their status: `remaining_fraction` or `remaining_amount`, `reset_time`, `reset_in_seconds`, and `disabled` (optional)" (example bucket `gemini-weekly`, `reset_time` "2026-07-06T07:50:32Z"). It is registered in `~/.gemini/antigravity-cli/settings.json`, outside the project, and run with `sh -c` (`cmd /c` on Windows). When `quota` is absent is not stated.
- **`agy -p /usage` (experiment).** The headless page still says slash commands "produce a text report rather than a standard event stream". On agy 1.5.9, `agy -p /usage --output-format json` exited 0 but **ran a model turn** (`num_turns` 1, 28,103 input tokens, `response` empty, a `read_file` action denied), so it spends Antigravity quota and gives no report. It is not a usage source.
- **Desktop scheduled tasks.** Unchanged quotes confirmed; also "If your computer sleeps through a scheduled time, the run is skipped", one catch-up run within seven days, the task History lists skipped runs with the reason, and Desktop offers its own **Keep computer awake** setting (Settings > Desktop app).

## Caveats

The Claude 5-hour window reaches the project only through the terminal status line (or, unverified, `claude -p /usage`); worker events have shown only the weekly window. `usage_snapshot.py` no longer assumes JSON from `agy -p /usage`.
